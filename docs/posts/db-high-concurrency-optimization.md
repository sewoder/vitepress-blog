> 核心原则：先 SQL/索引优化，再缓存卸读，然后架构分流，最后分布式扩展。每一步基于监控数据判断瓶颈，避免过度设计。

---

## 一、分层优化总览

| 层级 | 核心手段 | 主要解决问题 |
|---|---|---|
| 1. SQL 与索引 | 慢查询治理、联合索引、覆盖索引、SQL 改写 | 单点查询慢、索引失效 |
| 2. 缓存 | 本地缓存 + Redis + DB 多级缓存 | 高频读流量打到数据库 |
| 3. 读写分离与分库分表 | 主从分流、垂直/水平拆分 | 单库连接、IOPS、数据量瓶颈 |
| 4. 写入链路 | 批量写入、异步削峰、拆分大事务 | 高频写、锁竞争、瞬时洪峰 |
| 5. 热点与分布式 | Redis+Lua 预扣、MQ 拉平、分布式数据库 | 秒杀热点、极端扩展需求 |

---

## 二、SQL 与索引优化

优先治理慢 SQL，通常 Top 10 慢 SQL 贡献大部分数据库负载。

- **定位**：慢查询日志 + `EXPLAIN`，关注全表扫描、索引失效、隐式转换、回表过多。
- **索引**：优先联合索引，遵循最左前缀；尽量使用覆盖索引，减少回表。
- **SQL 改写**：避免 `SELECT *`；大分页用延迟关联；拆分大事务，缩短锁持有时间。
- **适用边界**：千万级以内、刚出现卡顿的系统，优先做这一步。

---

## 三、缓存：承接主要读流量

推荐多级缓存：**本地缓存（Caffeine） → Redis → 数据库**。

### 缓存三件套防御

| 问题 | 触发条件 | 防御手段 |
|---|---|---|
| 穿透 | 查询不存在的 Key | 布隆过滤器 + 缓存空值 |
| 击穿 | 热点 Key 过期瞬间 | 分布式锁重建 / 逻辑过期异步刷新 |
| 雪崩 | 大量 Key 同时过期 | TTL 随机扰动 + 多级缓存兜底 |

### 一致性策略

推荐 **Cache-Aside：先更新 DB，再删除缓存**，接受近实时一致性。

---

## 四、读写分离与分库分表

### 读写分离

- 主库承担写和强一致读，从库分担大部分读。
- 实时性要求高的读强制走主库。
- 实现方式：代理层（ProxySQL、MyCat）或组件层（ShardingSphere-JDBC）。

### 分库分表

- 优先**垂直拆分**：按业务拆库、冷热字段拆表。
- 再考虑**水平拆分**：按分片键分散数据，尽量避免跨分片事务。
- 平滑扩容：双写 + 全量迁移 + Binlog 增量同步 + 校验 + 灰度切换。

---

## 五、写入链路优化

- **批量写入**：合并单条 INSERT，减少事务和网络开销。
- **异步削峰**：引入 Kafka 等 MQ 缓冲写入洪峰。
- **拆分大事务**：缩短锁持有时间，降低并发影响。
- **硬件与参数**：OLTP 使用 SSD；合理设置 buffer pool，缓存热数据减少磁盘 I/O。

---

## 六、热点与分布式数据库

热点库存/秒杀场景：

1. **Redis + Lua 原子预扣**，拦截无效请求；
2. **MQ 拉平**扣减请求，异步落库；
3. 数据库用**条件更新**兜底，保证不超卖；
4. 可评估分布式数据库：TiDB、OceanBase、PolarDB。

---

## 七、监控闭环

至少覆盖：

- **系统层**：CPU、内存、磁盘 IOPS/吞吐；
- **数据库层**：QPS/TPS、慢查询、活跃连接、锁等待、主从延迟；
- **应用/中间件层**：查询耗时、错误率、缓存命中率。

形成：**监控 → 定位 → 优化 → 验证** 闭环。连接池不是越大越好，盲目调大会增加上下文切换开销。

---

## 八、按场景组合建议

| 场景特征 | 优先组合 |
|---|---|
| 读多写少 | 多级缓存 + 读写分离 |
| 写多、洪峰明显 | MQ 削峰 + 批量/异步写入 + 分库分表 |
| 存量系统刚卡顿 | 慢 SQL 治理 + 索引优化 |
| 数据持续膨胀 | 冷热分离 + 生命周期归档 |
| 秒杀/热点库存 | Redis+Lua 预扣 + MQ + 条件更新兜底 |

---

## 总结

按成本从低到高推进：**SQL/索引 → 缓存 → 读写分离/分库分表 → 写入链路优化 → 热点与分布式架构**。每层都应基于监控数据验证收益，避免为低并发场景引入不必要的一致性代价和运维复杂度。
